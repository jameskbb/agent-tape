# Security and threat model

AgentTape runs AI coding agents on your machine, records what they do, and can be
reached over HTTP. This page states what it protects, who it defends against, and the
mechanism behind each defence, with the code and tests that enforce it. Design decisions
are in ADRs 0005 (adapter security) and 0008 (secret redaction and storage).

## What is protected

| Asset | Why it matters |
|---|---|
| Secrets (API keys, tokens, passwords) | Agents see them and often echo them in output. |
| Your repositories and host filesystem | Agents write files; AgentTape runs Git commands. |
| The control plane | Anyone who reaches the API can start agents, approve risky actions, or read run history. |
| The record itself | Runs must be trustworthy evidence: complete, ordered, not silently rewritten. |

## Trust boundaries and actors

- **Local user**: trusted. On loopback (the default) no token is needed.
- **Network clients**: untrusted unless they present the API token (required whenever
  AgentTape binds beyond loopback).
- **Webhook senders** (GitHub, CI, scripts): untrusted; authenticated per trigger.
- **Agents and their output**: semi-trusted. Their output is data, never instructions to
  AgentTape. Their actions are constrained by the adapter security model below. An
  interactive Claude Code session AgentTape observes (it did not launch it) runs as you, so
  it can read the per-machine `hooks` and `mcp` capture tokens and post telemetry and
  findings about itself; what it reports is its own account, not independent evidence
  (T23, T25, and "Observed-session evidence is agent-reported" below).
- **Prompt inputs and payloads**: untrusted text that ends up in prompts and records.

| T24 | A hook slows, blocks, or fails the user's Claude Code session | Every AgentTape hook but one is a built-in `type: "http"` entry with an explicit 3s timeout (Claude Code's own default is 600s). The exception is `SessionStart`, for which Claude Code runs no `http` hook ("HTTP hooks are not supported for SessionStart"): it is an exec-form `type: "command"` hook running AgentTape's hook relay (`python -I -m agenttape.cli.hook_relay`, T30), whose own hard deadline is 3s inside a 10s hook timeout, and which always exits 0 and prints nothing (a SessionStart hook's stdout would become model context), so it can delay a session's start by interpreter start-up plus at most 3s and can never block or alter it. Claude Code treats a hook error or timeout as fail-open (an empty `{}` answer is exactly what a healthy hook also returns), so a slow or unreachable AgentTape never blocks a tool call. The endpoint answers `{}` before any database write: a bounded single-thread ingest queue (`MAX_PENDING_HOOKS`) processes the hook after the response is already sent, so a locked or slow database only ever slows AgentTape's own ingest, never the caller. A saturated queue (503) or a rate-limited hook (429) is dropped, never retried against the caller, and counted as dropped for its session; so is a hook that was answered but whose ingest then failed (a database still locked past the busy timeout rolls its whole write back), together with any drops it carried. A dropped count is written onto the session's row as `details.dropped_hook_events`, with a warning event, by whichever comes first: the session's next ingested hook, the next MCP finding resolved to that session (in the finding's own transaction, before the finding, so a drop that preceded a finding is always recorded before it), or the idle sweep closing the row (before the close and the verification it triggers). Past 10,000 sessions with a pending count (`MAX_TRACKED_DROPPED_SESSIONS`) the oldest count is written onto every open observed or hosted session instead of being forgotten. Pending counts are held in memory until then, so an AgentTape restart loses them; the restart itself is recorded as a gap as soon as a hook or finding from that session reaches the new process. Because a hook sent while AgentTape is not running fails silently, each observed or Herdr-hosted session row records which AgentTape process observes it (`details.observer_instance`); a later hook or MCP call arriving at a different process counts `details.observer_restarts` and records a warning event. ## Residual risks (known and accepted for V1)

- **Local user is trusted.** Anyone with your OS account can read the data directory,
  including raw logs (redacted) and the database.
- **Redaction is pattern and value based.** A secret the agent transforms (split across
  lines, base64-encoded) can evade it. Prefer secret references and short-lived tokens.
- **The command policy sees argv, not behaviour.** It judges the exact argument arrays
  AgentTape launches, so it is precise for `git` itself. An allowlisted program that is
  not git (an interpreter such as `python`, a build tool such as `make` or `npm`, or a
  wrapper script) can do anything its own code does, including running `git push`
  internally; the policy cannot see inside it. Shells are refused outright; allowlist
  only interpreters and build tools you would trust with your account. The same applies
  to Claude Code and Codex: the policy governs how AgentTape starts them, while what they
  do inside a run is governed by their own permission mode or sandbox (use `dontAsk` or
  `plan`, `read-only` or `workspace-write`, and tool rules). Git runs with your global
  and repository config: aliases are resolved, but hooks and other settings that execute
  programs (`core.hooksPath`, `core.sshCommand`) are caught only when passed with `-c`,
  not when they already live in your config files. (This is about commands AgentTape
  launches for an agent. AgentTape's own Git calls neutralize repository-configured
  programs; see T18. Repository-local filters, such as `git lfs install --local`, are
  turned off for those calls, and there is a small window in which config written between
  AgentTape's config read and the Git command is not seen.)
- **Agents act with your permissions** inside the working directory. Git isolation keeps
  them off your checkout; it is not a sandbox. Container or VM isolation is out of scope
  for V1.
- **No TLS termination.** Beyond loopback, put AgentTape behind a TLS reverse proxy
  (docs/DEPLOYMENT.md). Tokens sent over plain HTTP can be sniffed.
- **Evidence is only as complete as its sources.** Reads are known only from agent
  telemetry; the watcher can miss events under heavy load (recorded as degraded) and
  while AgentTape is offline (recorded as an incomplete window); final Git reconciliation
  still proves every net change to tracked and untracked files.
- **Herdr trust.** Anyone who can reach the Herdr socket controls the panes AgentTape
  uses; Herdr's own socket permissions protect it.
- **Single-user model.** No per-user accounts or roles; the actor name recorded in the
  audit log is self-reported.
- **Capture client credentials are plaintext at rest, and the observed agent can read
  them.** The hooks token lives in the user's own Claude Code `settings.json` (in the
  `http` hooks' `Authorization` header);
  `agenttape hooks setup` makes that file owner-only (`0600`) when it writes the token,
  and again on a repeat run if the mode was widened since, and `agenttape hooks status`
  warns when it is group- or world-readable. A second copy of the same token, for the
  SessionStart relay (T30), and the MCP client token each live in a `0600` file in the
  data dir. Owner-only files keep other accounts out, not your own processes: any
  program running as you, including the Claude Code session being observed, can read both
  tokens. Both are loopback-only and neither can read runs, but recording is itself the
  risk: a holder can put fabricated telemetry and findings on an observed or hosted run
  (next two bullets). `agenttape hooks setup --rotate` and `agenttape mcp register
  --rotate` replace either without needing to reinstall.
- **Observed-session evidence is agent-reported.** Hook events and interactive MCP
  findings are telemetry about a session that the session itself could also send, so the
  observed agent could fabricate them: for example, post a `PostToolUse` for a `Read`
  whose content it invented, then cite those lines. On a run whose evidence arrives
  through these endpoints (an observed run, or a Herdr-hosted Claude session), a `quote
  matches` verdict therefore proves the quote is consistent with what was reported, not
  with the repository. The citation header shows which one a verdict was checked
  against: "Git blob <id>" when the retained read's exact lines exist as a blob in the
  run's repository, "Reported output <hash>" when they were retained only from the
  reported output. A Git blob label means the lines exist as an object in that
  repository's object store, which any process that can write to the repository could
  also have added (`git hash-object -w`); it is not proof the lines were ever committed.
  AgentTape does not prefer a Git-anchored read over the newest recorded read that
  contains the quote, because that would check a different read than the one the agent
  last saw.
- **`never_read` means "no telemetry or hook reported this read", not "the agent never
  saw the file".** An observed or Herdr-hosted Claude Code session gets `never_read` only
  when its hooks covered every session whole (T24); these are the known limits of that
  record:
  - Claude Code loads `CLAUDE.md`, the files it imports, and files the user @-mentions into
    the conversation without a `Read` tool call, so no hook (and no stream-json event)
    reports them: a citation of one of those files is `never_read` on a covered observed
    or hosted run, and on a launched Claude Code run too.
  - A hook with a missing or wrong `hooks` token (a stale token after `agenttape hooks
    setup` replaced it, say) is never counted as dropped, since anyone could send one. An
    authenticated hook AgentTape cannot record is counted: for its session when its body
    names one (422 not shaped like a hook), otherwise (the client disconnected before its
    body was read, 413 over the body cap, 400 invalid JSON) as an unattributed drop written
    onto every observed or hosted session open when it was noticed, or closed within the
    60 seconds before. A run already verified when such a drop lands on it keeps its
    verdicts until its citations are re-checked.
  - A hook whose handling is delayed past Claude Code's 3s timeout but whose body AgentTape
    still receives is recorded late: if Claude Code went on to record a finding that
    reached the ingest queue first, the read is ordered after the finding and cannot back
    it. The hooks handler waits on nothing but the request body before it queues a hook
    (the token check runs on the event loop), so this takes the API process itself
    stalling for seconds.
  - Dropped counts wait in memory until a later hook, finding, or idle close of the same
    session writes them down, and an AgentTape restart loses them. A restart is recorded
    only when a later hook or finding from the session reaches the new process. Either way
    what is lost happened after the session's last recorded finding, so it cannot hide a
    read backing one; it only leaves the session looking more complete than it was.
  - Gaps are session-wide (CONTEXT-EVIDENCE.md): a gap recorded after every finding still
    makes a missing read `read_not_observed`. That errs toward the neutral verdict, never
    toward `never_read`.
- **Hosted sessions are matched by a reported directory.** A Herdr-hosted Claude session
  has no per-session secret, and the `cwd` a hook or an MCP call carries is reported by the
  caller, never checked against the calling process. Any process that holds the
  per-machine tokens (any process running as you, above) can report a directory inside a
  hosted attempt's workdir (shown in the run's detail) and record tool events and
  findings on that hosted run, wherever it actually runs. For a Herdr-hosted Claude
  challenge run this includes recording a review outcome for a finding the reviewer was
  shown, before or instead of the reviewer, and, by binding the hosted session row first,
  keeping the reviewer's own MCP server off that row for as long as it keeps calling (the lease in T25). A
  per-attempt capture token, as launched runs have, would close this; V1 does not mint one
  for Herdr-hosted attempts. It is bounded by the first bullet: a process running as you
  can already write the database directly.
- **Directory-only correlation has a registration race.** If two Claude Code sessions
  start at the same moment in one directory, a `record_finding` call from one can bind to
  the other's session row, and so land on its run, while that row is the only compatible
  candidate; likewise any Claude Code session started inside a hosted attempt's workdir is
  matched to that hosted run by directory alone. Such bindings are marked
  `cwd_sole_candidate` on AgentTape's session row (`details.mcp_resolved_by` or
  `details.resolved_by`); the marker is not yet shown in the UI or API.
- **Retained evidence** (the file content T16 describes). The content a citation verdict
  is decided from is kept once per read: a Git blob reference is used only when the read
  starts at line 1 with no gaps, was not cut by the size cap or by its own `limit`, and is
  unredacted, and the blob holds exactly those lines, so the reference always points at
  exactly the content that would otherwise have been copied, never at more than the
  redacted recording; every other read is a redacted, size-capped local copy. Both forms
  die with their run through the same retention cleanup that removes everything else
  under `runs/<run_id>/...`, with no separate retention code path.
- **Adversarial review is model judgment, never proof.** A review outcome
  (`upheld`/`refuted`/`inconclusive`) is one agent's own reading of another agent's claim,
  labelled `"model judgment"` and `counts_as_proof: false` everywhere it appears; it never
  writes or changes a citation verdict. The tests in `test_findings_review.py`,
  `test_finding_review.py`, and `test_finding_review_injection.py` prove how the reviewer's
  prompt is built and delivered (untrusted findings stay inside the delimited block, a
  secret reference never resolves into it) and that a scripted, no-model reviewer can
  genuinely disagree with a finding through the real pipeline. They do not prove that a
  real language model resists prompt injection, and they say nothing about a real model's
  sycophancy or susceptibility to a crafted finding. No test in this suite calls a model.

## Reporting a vulnerability

Report issues through GitHub private vulnerability reporting (the repository's Security tab, "Report a vulnerability"), not a public issue, with steps to reproduce and the affected version (`agenttape --version`).
